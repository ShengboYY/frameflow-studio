# Future Product 候选规划与待验证假设（Track B）

## 1. 定位与边界

更新日期：2026-10-29（Asia/Shanghai）。本文根据用户提出的“Assessment 后演进为真实 AI
素材制作平台”的方向，以及现有 task/template/asset/identity 候选边界进行分析。
**所有产品能力均为假设或候选需求，尚未验证用户需求、优先级或商业可行性；不构成当前验收标准。**
这里的阶段顺序也是候选方案，没有承诺日期、技术供应商、API、数据模型或实现计划。

Track A 只以 Assessment R-01～R-14 原文为当前业务验收依据，见
[requirements.md](requirements.md)。本轮已在用户指定的 Chrome 卷面读取完整原文及内嵌参考图，
来源、读取日期与定位方法见该文档第 1 节；下文使用真实 R 编号关联当前能力。
只有关联的当前需求已经确定，未来增强仍是假设。现有工程只有骨架，不能将已确定需求写成已实现能力。
2026-10-30 用户已确认以预置账号登录/退出满足当前身份方案，不做注册；具体设计见 detailed-architecture.md。
下文 FP-04 的未来范围是注册和完整账号治理，不再包含当前已选的基础登录。

规划遵循以下规则：

1. 先完成 Assessment 的最小要求；未来能力不得成为 MVP 的隐藏前置依赖。
2. 复用 [architecture.md](architecture.md) 和 [ADR-006](architecture-decisions.md#adr-006基于-ddd-skill-改为分层优先的六边形包结构)
   的纯 Domain、Case 编排、Port/Adapter 边界，不因未来规划改造当前实现。
3. “现在预留”优先指保持概念和依赖边界清晰，不等于创建空接口、表、字段、路由或框架。
4. 实际 MVP 用例确实需要外部能力时才定义最小 Port；未知业务规则不提前冻结公共 API 和存储模型。
5. 当前必做的异步任务、轻量身份、个人历史、图片预览和刷新恢复不能推迟到 Track B。
   本文只讨论这些能力之外的产品增强；Compose 按 R-14 保持推荐等级。

### FP-01：真实 AI 图片与视频生成

- **业务价值与场景假设**：创作者可能希望将模板和输入素材转换为可使用的图片或视频，
  并能观察耗时较长的生成过程。图片与视频是否同属一个创作需求，需要分别验证。
- **与 Assessment 的关联**：R-04～R-06 已要求三阶段 Mock 和确定性模拟控制，R-09 只要求图片预览、明确不要求视频。
  未来可以从模拟生成边界探索真实能力，但远程提交/回调和视频流程可能改变任务语义，不能承诺只替换适配器即可完成。
- **模块/模型影响**：可能影响 task 的完成/失败语义、输入参数、输出数量以及 asset 的结果引用。
  远程提交、查询、回调是协议机制，不自动等同于领域状态。只有业务出现独立生命周期才考虑新概念。
- **未来扩展边界**：生成业务能力可按现有规划位于 `domain.task.adapter.port`，
  由 Infrastructure 适配真实服务；远程协议和 DTO 留在 gateway，Case 协调调用和短事务。
  这里只讨论边界，不确定方法签名。
- **现在是否预留**：是，仅保持任务不依赖外部 SDK/协议；首次实际需要生成能力时再定义最小接口。
  不为视频预建时长、帧率、镜头等字段，不假定图片与视频能共用全部契约。
- **为何推迟实现**：题面明确不要求真实 AI，R-09 不要求视频；真实服务接入、调用成本和异步语义也尚未确认。
- **待验证假设**：目标用户优先需要哪种媒体？输入、质量、耗时和费用能否满足具体场景？
  先用一个明确场景的小规模试验决定是否推进，再评估产品状态与 API 的变化。

### FP-02：多模型或多 Provider

- **业务价值与场景假设**：不同模型可能适合不同风格、质量或耗时目标；服务不可用时可能需要替代能力。
  用户主动选择模型和系统自动路由是两个不同假设。
- **与 Assessment 的关联**：R-05/06 的 Mock 只需按固定三步执行并可控制失败与耗时，没有模型选择或供应商要求；
  多模型选择、自动回退和供应商管理不进入当前 AC。
- **模块/模型影响**：可能产生模型能力、选项、路由策略及执行来源信息。task 只承载业务需要的信息，
  不把所有供应商参数塞成无约束配置；也不急于独立建立 generation 领域。
- **未来扩展边界**：在生成 Port 后增加实际需要的适配器，协议差异留在 Infrastructure。
  若“选择何种能力”成为业务规则，再讨论它应归属的领域策略和与 Case 的协作。
- **现在是否预留**：部分预留，主要防止供应商 DTO/错误码进入领域或公共 API；
  不创建 Provider 注册中心、插件系统、通用参数全集或策略框架。
- **为何推迟实现**：没有多个真实需求时，抽象容易被第一个供应商误导；回退还可能重复生成并产生费用。
- **待验证假设**：单一能力的实际不足是什么？至少两个已验证场景是否需要可替代模型？
  何种失败允许回退、费用由谁承担、是否需要保留来源，均待明确。

### FP-03：云对象存储

- **业务价值与场景假设**：用户可能需要跨设备访问素材，应用可能需要跨实例读取输入、
  保存大媒体或较长时间保留结果；这些需求尚无容量与保留期证据。
- **与 Assessment 的关联**：R-03 明确允许后端本地目录或容器数据卷，且素材必须服务端可用；
  R-05/09 要求可预览结果。云存储不能成为这两项当前能力的额外前置条件。
- **模块/模型影响**：可能影响 asset 的内容标识、存储引用、访问有效期和删除语义；
  数据库元数据与实际对象跨系统写入可能产生不一致，需要在实际用例中确定处理策略。
- **未来扩展边界**：遵循候选 AssetStorage 边界（`domain.asset.adapter.port`），
  Infrastructure 处理本地/云存储 I/O；文件访问和授权由实际用例决定，Repository 不混入存储服务职责。
- **现在是否预留**：是，概念上区分素材身份、持久存储定位和可过期的访问地址，避免本地绝对路径成为业务身份。
  不预建 bucket、签名 URL 字段、CDN 或多存储商抽象。
- **为何推迟实现**：存储区域、权限、保留期、成本和部署需求尚未验证，当前无需为未来基础设施增加配置与依赖。
- **待验证假设**：文件规模、跨实例需求和保存期限是什么？服务端中转还是直传更适合？
  删除、孤立对象清理与访问失效如何影响用户，需先确定再设计。

### FP-04：用户注册与完整账号授权

- **业务价值与场景假设**：稳定账号可能帮助用户跨设备保留创作记录，并管理私有资源。
  团队协作、角色和多租户仍是独立假设，不能从“有账号”推导出来。
- **与 Assessment 的关联**：R-10 已要求自行设计身份和个人任务记录方案，R-08/09 要求切换上下文正确、刷新后恢复个人记录。
  具体身份方式由实现自行选择，且题面不强制额外身份服务；注册、密码、第三方登录不是当前必做。
- **模块/模型影响**：可能影响 identity 中的主体概念，以及 task/template/asset 的归属规则。
  认证证明“是谁”，资源所属域决定“能做什么”；现有 identity 包说明不等于已有用户聚合。
- **未来扩展边界**：Trigger 取得可信调用者，Case 协调资源权限；纯领域模型不依赖认证框架。
  未来身份服务可通过边界适配，不让每个领域自行解析凭据。
- **现在是否预留**：是，在需要身份的实际用例中保持传输身份与资源归属的边界清晰；
  当前只设计预置登录所需最小账号表；不预建注册/改密流程、JWT/OAuth 契约、角色权限树或租户字段。
- **为何推迟实现**：账号生命周期与既有访客数据如何关联没有确定规则，过早实现会冻结不可逆的数据归属假设。
- **待验证假设**：个人还是团队使用？登录方式是什么？访客是否转成账号、历史素材归谁、
  账号删除与作品保存如何协调？未确认前不定义迁移或合并规则。

### FP-05：模板创建、编辑和版本化

- **业务价值与场景假设**：创作者可能希望维护可复用的制作方式，调整输入和生成规则，
  并让过去的任务仍能解释当时使用的模板。
- **与 Assessment 的关联**：R-02/03 要求自造模板目录、详情与素材限制，种子文件或数据库均可，明确不要求模板 CRUD；
  模板编辑器、发布审批、版本历史或回滚不进入 MVP。
- **模块/模型影响**：template 可能从查询概念发展为有修改规则的聚合。
  task 需要在实际历史一致性要求下选择模板引用、版本引用或执行输入快照；三者不能未经分析同时引入。
- **未来扩展边界**：模板管理用例归相应 Case，模板规则由 template 所有；
  task 通过公开能力取得允许使用的信息，不访问模板内部 Repository/DAO 或复制完整模板对象图。
- **现在是否预留**：仅记录“模板变化后历史任务含义是否变化”的问题。
  若 MVP 原文已要求此一致性则现在解决；否则不为未来预建版本表或把模板固定为某种 DSL。
- **为何推迟实现**：谁编辑、何时可用、哪些字段可变、历史可复现到什么程度均未知，编辑器和版本模型维护成本较大。
- **待验证假设**：用户是否真的需要自建模板？草稿与发布是否必要？仅保留输入快照能否满足历史解释，
  还是需要可引用版本？即使保存版本，模型服务变化也可能使结果无法完全复现。

### FP-06：任务队列、重试与恢复

- **业务价值与场景假设**：长任务和多用户负载可能需要排队，失败或进程中断后可能需要继续处理，
  以降低重新提交的成本。可见排队、人工重试、自动重试、重启恢复是不同候选能力。
- **与 Assessment 的关联**：R-04 已要求页面关闭后继续后台执行，允许排队或并行；R-05/06 要求状态持久化及失败中断。
  排队执行本身可以是当前实现选择，不等于必须有持久 MQ。范围排除正文明确不要求重启自动恢复，
  后端幂等、断点续跑、自动重试可讨论但非额外扣分项；R-13 要如实说明限制。
- **模块/模型影响**：可能涉及 task 的逻辑任务与执行尝试、并发控制、重复投递、幂等和结果归并。
  基础设施的“至少一次投递”不意味着业务应重复计费或产出，也不能直接等于业务重试。
- **未来扩展边界**：应用执行派发按现有规划位于 `cases.task.port`；适配器负责队列/执行机制，
  独立执行 Case 编排业务，Domain 维护合法状态。未来确有可靠性要求再比较持久化派发、Worker 等方案。
- **现在是否预留**：是：当前已有异步写入需求，提交后派发、短事务、状态条件更新/乐观锁及可信执行上下文应在首次实现时考虑。
  这些属于现有工程原则；本轮不新增状态、执行尝试表、MQ、Outbox、恢复扫描或分布式锁。
- **为何推迟实现**：可靠性等级、吞吐、重试费用与取消语义尚未确定；现在实现完整可靠执行系统会扩大交付范围。
- **待验证假设**：可接受等待多久？服务超时是否可能已成功？外部操作是否可幂等？
  重试整项还是单步骤、上限与退避如何决定、谁发起恢复，需结合真实故障和产品承诺验证。

### FP-07：可配置生成 Pipeline

- **业务价值与场景假设**：当多种制作流程反复组合相同能力时，配置步骤可能减少重复开发，
  例如把多个已验证生成能力组成新的制作方式。是否需要用户编辑与可视化界面仍未验证。
- **与 Assessment 的关联**：R-05 已固定素材检查、模拟生成、结果整理的顺序和独立可观察边界；
  当前用清晰用例代码表达即可，固定三步不足以要求可配置 Pipeline。
- **模块/模型影响**：可能涉及步骤输入输出、依赖、流程版本、部分失败和任务执行快照；
  这些概念不自动成为 task 聚合内部对象，模板配置与执行记录的责任要分别验证。
- **未来扩展边界**：已确认的业务能力保留各自 Port；Case 编排与执行机制分离。
  若出现真实且稳定的组合需求，再评估流程配置的所有权及是否需要独立能力边界。
- **现在是否预留**：有限预留，只保持状态规则不依赖某个线程池或执行框架；
  不增加节点基类、通用上下文 Map、DAG 引擎、配置 DSL 或工作流框架。
- **为何推迟实现**：步骤变化证据不足，容易把尚不稳定的业务模型冻结成配置语言，并扩大验证与调试成本。
- **待验证假设**：多个真实流程是否存在稳定的复用结构？配置由开发者还是用户维护？
  类型约束、流程迁移、旧任务执行和失败定位是否值得引入通用引擎，需用具体流程比较。

### FP-08：制作结果管理与分享

- **业务价值与场景假设**：用户可能需要查找、分类、复用或交付作品；分享可帮助他人查看成品。
  私密交付、公开展示和团队协作是不同使用场景。
- **与 Assessment 的关联**：R-09 已要求个人历史、创建时间、状态、图片预览或失败原因，明确不要求下载、删除、重新制作或视频。
  当前历史与预览必须完成；收藏、标签、作品集、分享链接、下载控制及协作者属于未来候选。
- **模块/模型影响**：结果可能仍是任务输出关联素材，也可能在拥有独立发布/删除生命周期后形成新概念。
  不因有“结果页”就新建 Result 聚合；分享规则可能涉及 asset、身份和结果的公开能力协作。
- **未来扩展边界**：先区分任务执行记录、可保存的成品和访问授权；
  由 Case 协调相应领域能力，存储适配器只提供 I/O，不能代替业务分享授权。
- **现在是否预留**：仅避免将短期文件访问 URL 作为结果身份或唯一持久引用；
  不预建结果管理域、分享 token、ACL、作品集或标签模型。
- **为何推迟实现**：可见范围、过期/撤销、删除关联和保留策略尚未确定；分享会形成新的公共行为与访问契约。
- **待验证假设**：作品主要给谁看？分享是否匿名、是否到期/撤销？源任务或账号删除后分享是否有效？
  用真实交付场景确认后再决定结果生命周期和访问模型。

## 3. 值得现在考虑的架构扩展点与取舍

这些建议与现有文档对齐，不是新 ADR、不触发架构或业务代码修改。
接口名称是既有候选能力名，不能据此认定接口已经存在或签名已确定。

| 扩展点 | 现在保护什么 | 以后可能怎么扩展 | 取舍与触发条件 |
| --- | --- | --- | --- |
| 生成能力 / MediaGenerator | 领域状态不耦合 SDK、远程 DTO、Provider 错误码；有实际用例才定义 Port | 真实生成适配器，再按需要支持多个模型 | 第一种真实服务可能改变同步/异步语义；不能保证所有服务无损替换，届时审查契约 |
| 素材存储 / AssetStorage | 素材身份、存储引用和访问地址分清；I/O 留在 Infrastructure | 本地实现演进到对象存储及访问签名 | 直传、多段上传、对象清理可能新增用例，不提前用巨大接口覆盖 |
| 应用派发 / TaskDispatcher | 派发机制与任务执行 Case 分离；业务用例需要时才建接口 | executor 演进到持久派发或 MQ/Worker | 引入队列不自动解决提交后崩溃、重复消费和外部幂等；需要明确可靠性承诺 |
| 身份与归属边界 | 传输身份提取不渗入聚合，资源所属域拥有访问规则 | 接入真实认证，并按实际场景演进主体关系 | 访客与账号的迁移可能影响数据归属，不能提前固定为字符串替换或新增 user_id 即可 |
| 模板与历史一致性 | 不混淆当前模板与任务创建时采用的含义；按 MVP 实际要求处理 | 快照或版本引用等具体方案 | 无历史一致性要求时不提前建版本系统；需求出现后比较存储和迁移成本 |
| 聚合与跨域协作 | 按原子一致性规则定聚合；跨域经公开能力和 Case，Domain 保持纯 Java | 实际独立生命周期出现后再评估新领域或构建模块 | 现有四个包只是候选边界，不是已确认的四个限界上下文；不现在拆微服务 |

保持单 Maven 工程、单体部署与现有框架即可承载当前分析。
未来需求若改变公共 API、身份含义、状态或持久化保证，需另行分析兼容与迁移，并更新相关 ADR/API 文档；
不能将这类变化全部归为“换一个适配器”。

## 4. 应推迟实现的内容

以下超出已读取原文的增强，推迟至具体假设验证之后；不包含第 2 节已区分的当前必做基础能力：

- 真实 AI 服务及媒体专项参数、多 Provider 管理、模型路由和自动回退。
- 云存储 SDK、CDN、直传链路、多存储后端及生命周期清理系统。
- 完整账号系统、团队/租户/角色模型、访客合并和账号迁移。
- 模板编辑器、发布/回滚、版本仓库和流程配置语言。
- MQ/Worker、Outbox、自动重试/恢复、通用调度或工作流引擎。
- 独立结果管理领域、分享/公开发布、作品集、分类标签与协作功能。
- 为上述能力提前添加的空接口、空模块、预留表/字段和未使用依赖。

推迟的原因是业务承诺尚未确定、不能增加当前验收范围，也要避免过早固定模型。
这不推迟 Assessment 原文要求的错误处理、数据保留或并发一致性，也不降低既有工程约束。

## 5. 假设验证与候选演进顺序

以下按风险和依赖安排探索，没有将 FP 项目排为承诺交付清单；任何假设均可被验证结果否定。

| 候选阶段 | 进入条件 | 可以探索什么 | 推进依据 |
| --- | --- | --- | --- |
| A：完成 Assessment | 原文已读取；先完成领域建模与必要设计 | 仅 Track A 的后续实现与验收；本轮仍只做分析 | 强制条目有来源、有 AC、有证据；已知限制不掩盖验收缺口，Compose 保持推荐等级 |
| B：验证一种真实制作场景 | Assessment 结束，确认目标用户和实际输入/输出需求 | 优先验证 FP-01 的一种媒体；存储或身份只有在该场景确有需要时再探索 | 质量、耗时、成本和使用价值有实际观察，能决定是否继续 |
| C：验证持久使用需求 | 用户确有重复创作、跨设备或长任务使用 | 按观察选择 FP-03/04/06/08 中必要部分，非一并实施 | 保存、权限、失败恢复、结果交付的具体规则获得确认 |
| D：验证复用与可配置性 | 多个真实场景证明固定实现的局限 | 选择性探索 FP-02/05/07 | 多模型、版本或配置带来的收益足以覆盖其模型及运维成本 |

每次产品验证应记录：目标用户、待验证问题、最小试验、观察结果、规则变化、继续/推迟/否定的结论。
阈值和成功指标由对应场景确认，本文不自行规定响应时间、可用率、容量或商业指标。

## 6. 后续 DDD 领域建模重点

1. **统一语言与生命周期**：任务、一次执行、生成请求、阶段、输入素材与成品分别指什么？
   哪些有独立身份和生命周期，哪些只是投影、值对象或技术记录？
2. **聚合一致性**：哪些状态/结果/失败信息必须原子变化？是否存在部分成功？
   多个步骤或外部调用不应因此被放进一个长期数据库事务。
3. **模板历史语义**：任务采用当前模板、某个版本还是输入快照？模板变更、下线与删除是否影响已提交任务？
4. **所有权与授权**：调用者、任务创建者、素材所有者和分享访问者是什么关系？
   账号或团队的引入是否改变这些关系？现阶段不冻结合并、转移或跨租户规则。
5. **异步幂等与费用**：逻辑任务和执行尝试是否分开？谁能重试，怎样处理“远端可能成功但本地超时”？
   状态幂等、消息幂等和外部收费幂等需要分别分析。
6. **跨系统一致性与结果寿命**：元数据、文件内容、任务输出和分享链接能否独立失效？
   哪些失败需要补偿、清理或恢复，哪些只是临时访问失效？
7. **可变能力与稳定契约**：图片/视频及不同模型真正共用的业务语言是什么？
   先验证再抽象，避免统一 Provider DTO 或通用 Pipeline 配置替代领域模型。
8. **边界是否成立**：task/template/asset/identity 是否足够？出现独立规则后再评估新边界；
   不把每个实体都变成聚合，也不把每个未来能力都拆成服务。

以上问题是未来增强的后续建模输入，尚不是确定的业务不变量或验收标准。
当前已确定的三步顺序、失败中断、完成不回退、请求/执行失败区分、个人记录及跟踪隔离，
应按 requirements.md 先建模，不能因未来规则未确定而推迟。
